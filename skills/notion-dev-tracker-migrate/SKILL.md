# notion-dev-tracker-migrate

## 移行先を確認する

Gitルートの `.notion-dev-tracker.json`、[DBスキーマ](../notion-dev-tracker/references/schema.md)、[運用規則](../notion-dev-tracker/references/workflow.md)、[タスク本文](../notion-dev-tracker/references/task-template.md)を読む。新形式の設定・実スキーマ・Projectだけを利用する。旧設定の読み替え、旧Notionスキーマの更新・修復、リセット・初期化、今回の既存導入先向けクリーン切替は対象外。未対応の設定・スキーマなら停止して不足・不整合を報告する。

新形式の初期設定が不足する場合はnotion-dev-tracker-setupへ案内する。新形式でIssue接続だけが未設定でも、有効なタスク設定があればタスク移行を続行できる。Issueを未設定・未確認と報告し、タスク移行のためにIssue DBの新設を要求しない。

利用者の接続で実スキーマとProjectを取得し、repository、データソースID、project_page_id、`status_values.task_status`・`project_status`・`approval_status` を照合する。既存タスクはProjectで絞り、完了済みも含む移行対象の全範囲をページ送りの最後まで確認する。取得失敗を0件とせず、取得範囲外の件数を断定しない。

対象はリポジトリのタスク管理ファイル等から、合意したタスクを取り込む一般機能。元資料をIssueへ自動分類せず、既存のIssueと関係も合意した対象以外は保持する。移行の同意は、取り込んだタスクの実装許可ではない。

## 現状を調べて案を示す

1. タスク管理ファイル、AGENTS.md、関連文書・スクリプトを読み、管理元、タスク単位、状態と根拠、依存、最新報告の所在を確認する。1タスクは独立して優先順位付け・引継ぎ・検証・受け入れできる仕事とし、ファイルや実装手順ごとに機械分割しない。調査タスクにPRやマージを必須としない。形式は実物から判断し、食い違いと不明点を示す。
2. 対象範囲・件数、ID、状態、依存、詳細を列または本文へ移す対応を示す。既存Notionデータとの照合、追加・更新、重複・競合の扱いを具体化する。共有仕様は正本への参照でつなぐ。元の管理元の切替、元ファイルの削除や旧運用停止を含めるなら、対象と時期を案に明記する。日々の状態をNotionとローカルJSONの両方へ更新する運用は作らない。
3. 案を示して利用者の同意を待つ。初期設定依頼や候補発見は調査・提案までの根拠であり、取込みの許可ではない。「提案だけ」「保存しない」を優先する。同意済み範囲は続け、案の変更は該当差分への同意を得る。

## 同意された案を実行する

4. 管理元と移行先を再読取し、合意した対応で取り込む。元IDと実際のNotionページIDの対応を保持し、既存再利用と新規作成を区別する。`project + task_id` で特定し、別Projectの同じIDや同名タスクを変更しない。複数一致なら停止する。元資料の位置、状態の根拠、目的・範囲・完了条件・検証方法・最新要約を本文に残す。不明な承認・日時・担当・完了根拠・コミットは推測しない。元のDone表記だけで受け入れ済みとみなさず、根拠不足の扱いは案で合意する。
5. 対象ページを特定してから依存関係を設定し、実ページで自己参照・循環を検査する。Issueの関連を変更する合意がある場合は、実ページIDとProjectを確認し、タスクと同じProjectであることを検査する。更新直前に再読取し、合意した列・本文・対象だけを変更する。更新後に保存結果を確認する。途中失敗・結果不明・再実行では保存済みページと元IDの対応を調べ、重複を作らず未保存部分から再開する。
6. 完了済みを含む合意範囲について、件数、ID、状態、主要情報、本文、依存と逆参照を移行元と照合する。取得・保存・検証済みと未確認を分けて報告し、結果不明を成功として扱わない。管理元の切替は合意した範囲の検証後に反映し、AGENTS.mdの案件固有規約と対象外の管理指示を保持する。未解決で切替条件を満たさなければ既存管理元を維持する。元ファイル削除や旧運用停止は具体的に合意した対象・時期に限る。通常運用をnotion-dev-trackerへ引き渡し、次の操作を示す。
