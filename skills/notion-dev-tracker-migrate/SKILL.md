# notion-dev-tracker-migrate

## 移行先を確認する

Gitルートの `.notion-dev-tracker.json` と、このスキルからの相対パス `../notion-dev-tracker/references/schema.md` を読む。タスク移行に必要な設定が不足する場合は `notion-dev-tracker-setup` で保存先・epic DB・backlog DB・対象epicの初期設定を完了する。Issue未設定の既存設定でも、必要なタスク設定が有効なら移行を続行できる。Issueは未設定と報告し、タスク移行のためにIssue DBを新設する必要はない。

利用者のNotion接続で実スキーマと対象epicを取得し、設定の `repository`、データソースID、`epic_page_id` が対象と一致するか確認する。`status_values` の `task_status`、`epic_status`、`approval_status` を保存値と照合する。既存タスクはepicで絞り、必要なページ送りを最後まで行う。

このスキルの対象は既存タスクの移行。元資料をIssueへ自動分類・移行せず、既存のIssueやその関連も合意した対象以外は保持する。

## 現状を調べて案を示す

1. リポジトリのタスク管理ファイル、`AGENTS.md`、関連文書や管理スクリプトを読み、管理元、タスクの単位、状態とその判定根拠、依存関係、最新報告の所在を確認する。形式や変換規則は実物から判断し、情報の食い違いと未解決点を示す。
2. 対象範囲と件数、ID・状態・依存・詳細情報をどの列または本文へ移すかを提案する。既存Notionデータとの対応、追加・更新する範囲、重複や競合の扱いを具体例で示す。元の管理方法やタスク管理元の指定を切り替える場合は、対象ファイルと切替時期も案に含める。
3. 提案を示してユーザーの同意を待つ。初期設定の依頼や候補ファイルの発見は、調査と提案を進める根拠として扱う。取り込みは提示した案への同意後に行う。合意済みの範囲は続行し、案を変更する必要がある場合は該当差分の同意を得る。

## 同意された案を実行する

4. 管理元と移行先を読み直し、合意した対応付けで取り込む。元タスクの識別子とNotionページの対応を保持し、既存行の再利用と新規作成を区別する。`epic` と `task_id` で対象を特定し、同名だけで同一タスクと判断しない。元資料の位置や状態の判定根拠を本文に残し、不明な承認・日時・完了根拠は未設定とする。
5. 対象タスクのページを特定してから依存関係を設定する。途中で失敗した場合、結果が不明な場合、または再実行する場合は、保存済みのページと元タスクの対応を確認して残りから再開する。変更は合意した列・本文・対象タスクに絞る。
6. 件数、状態、主要情報、依存関係を移行元と照合し、結果と未解決項目を報告する。合意したタスク管理元の切替は検証後に反映し、日々の管理を `notion-dev-tracker` に引き渡す。元ファイルの削除や旧運用の停止は、提案で具体的に合意した対象とタイミングに従う。
