# notion-dev-tracker-setup

## 入力と配布物

対象Gitリポジトリ、利用者のNotion接続、保存先を使う。[DBスキーマ](../notion-dev-tracker/references/schema.md)と[設定例](../notion-dev-tracker/references/project-config.example.json)を読む。新規導入と、互換性のある新形式の再セットアップを担当する。既存の業務データを試験用に変更しない。

対象リポジトリの設定、または選択した接続先の一式が旧形式なら未対応として停止し、不足・不整合を報告する。保存先に同居する対象外の旧DBは選択・変更せず除外し、同居だけを理由に有効な新形式の一式を拒否しない。旧キーの読み替え、旧スキルの自動引継ぎ、旧Notionスキーマの改称・修復、データ削除・初期化をしない。旧設定を残したまま新設定を作って拒否を迂回しない。既存導入先のクリーン切替はこのスキルの対象外。

## セットアップ

1. Gitルート、remote、手元の変更、AGENTS.md、既存スキルと設定を確認する。remoteをWeb URLに正規化し、末尾の.gitを除く。GitHubのSSH形式とHTTPS形式は同じリポジトリとして扱う。対象remoteが決まらなければ利用者に確認する。実際のタスク管理元を調べ、移行候補のパスと根拠を控える。設定がある場合は新形式であることを先に検証する。
2. 利用者のNotion接続の読取・作成・更新・リレーション・クエリ機能を確認する。依頼または有効な設定の保存先を使う。未指定なら、新規DBを作る親ページか既存DBのリンクを尋ねて待つ。アクセス失敗は未確認として報告し、0件や空の保存先と判断しない。
3. 指定保存先を取得する。既存設定がある場合だけ保存済みのデータソースIDとProjectページIDを取得し、保存先の一式と照合する。新規導入では未作成のIDを要求しない。新形式でIssue接続が未設定ならProject・Backlog側を先に照合し、Issueの取得・追加は接続を補う依頼がある場合に行う。指定した親ページの子DB、または指定DBに接続されたリレーション先を確認する。作成先の親ページを特定できなければ確認する。同じ名前という理由だけでDBを選ばない。新旧DBが同じ親ページにあっても、`project` の参照先と逆参照を持つ新形式の一式を実体で識別する。複数候補が残れば、名前で推測せず確認を求める。
4. 選択した接続先の実スキーマを同梱の契約と照合する。互換性のあるDBを再利用し、新規導入の空の保存先では[DBとリレーションの作成](#dbとリレーションの作成)に従って3DBを作る。新形式のIssue追加依頼では既存の一式を照合して不足部分だけを補う。Issue追加を含まない再セットアップでは未設定のままタスク側を続ける。選択した一式が旧形式や非互換なら停止し、列名・型・参照先の変更やデータ破棄を試みない。新規作成が途中まで成功している場合は、確認できる作成記録と実際のID・非リレーション列・作成済み関係を再取得し、同じ一式の未作成部分だけをこの作成順で続ける。対象を特定できなければ推測で再作成しない。双方向リレーションの逆列を重複作成しない。
5. `status_values` のtask_status・project_status・approval_statusを実際の選択肢に対応付ける。Issueを新規導入・追加・再利用する場合はissue_statusも照合し、未設定のままの場合は必須にしない。新規DBにはスキーマの既定値を使う。日本語等の状態名とtypeは意味が一意に対応すれば保持し、曖昧なら確認する。Status型とSelect型、Statusグループを区別する。利用するDBを再取得し、型、状態、参照先と逆参照を検証する。必要な機能が接続にない場合は、完了した範囲と未完了を報告する。
6. agent-projectを正規化したrepositoryで照合し、一致する1件を再利用する。有効な設定がある場合は設定のProjectページも同一であることを確認する。なければ識別可能なnameと正規化repositoryで作成する。複数一致や設定との不一致では作成・更新を止める。Projectのownerは人間側の既定責任者とし、不明な担当・状態は推測しない。タスクの全件DoneだけでProject状態を変更しない。
7. `.notion-dev-tracker.json` に実際のrepository、project_data_source_id・backlog_data_source_id、project_page_id、status_valuesを保存する。Issue接続を確認できた場合はissue_data_source_idとissue_statusも保存し、未設定値は推測で補わない。認証情報は記録しない。新規導入は3DBを準備する。新形式でIssue接続だけが未設定の既存設定は、スキーマの規則に従いタスク操作を継続できる。Issue接続を完了できない場合は未設定・未確認と報告し、旧設定の互換対応と混同しない。
8. 配布元のmainからまとめて取得した3スキルを、referencesを含めて `.agents/skills/` に配置する。手元の編集と競合する場合は差分を示して確認する。配置後、notion-dev-trackerの `metadata.version` を設定の `skill_version` に記録する。
9. AGENTS.mdの `notion-dev-tracker:start` / `notion-dev-tracker:end` 管理区間を追加・更新する。同じ管理区間を重複させず、区間内外の案件固有規約と既存の管理元を保持する。旧管理区間を自動変換・削除しない。既存の管理元との矛盾がある場合は勝手に切り替えず報告する。移行前は既存管理元が有効であることを明記し、新しい区間の現状照会指示がそれを上書きしないようにする。管理区間には設定と通常スキルのパス、実際のProjectリンク、移行案への同意と検証後に管理元を切り替えることを記す。移行済み・新規導入なら、Notionのタスク状態・優先順位・依存・承認・報告・受け入れを正本とする旨を記す。
10. Projectページに案件リンクと関連仕様・タスク・Issueへの入口を用意する。既存の入口は再利用し、再実行で同じブロックを追加しない。共有仕様の正本を明示し、詳細を各タスクへ複製しない。リンクドビューの自動作成は必須としない。接続で可能なリンク・ページ作成と、利用者が画面で設定するビューを区別して報告する。
11. 配置したnotion-dev-trackerを読み、Projectと取得対象を確認する。通常の現状照会は未完了タスク・未処理Issueを中心とし、必要な関連・依存をたどる。全件件数を報告する場合は完了済みも含め必要なページ送りを最後まで取得する。取得範囲・未取得・未確認を明示し、未取得を0件としない。DB作成・再利用、Projectリンク、件数と取得範囲、配置ファイル、スキル版、未解決事項を報告する。
12. タスク管理ファイルの候補があれば、パスと根拠を示してnotion-dev-tracker-migrateの実行を提案する。希望されたら調査と具体案へ進み、取込みは案への同意後に行う。Setupだけでは管理元を切り替えない。

同じ設定で再実行する場合も、DB・Project・設定・配布物・管理区間・資料入口を実体で照合する。更新直前に再読取し、担当範囲だけを変更して更新後に確認する。失敗や結果不明では保存済み範囲を確認してから残りへ進み、重複作成や未確認の完了報告を避ける。

## DBとリレーションの作成

1. agent-project、agent-backlog、agent-issueをtitle列と非リレーション列とともに作り、実際のデータソースIDを取得する。互換性のある既存DBは再利用する。
2. agent-backlog.project から agent-project への双方向リレーションを作り、逆名を tasks にする。
3. agent-backlog.dependencies から同一DBへの双方向リレーションを作り、逆名を dependents にする。
4. agent-issue.project から agent-project への双方向リレーションを作り、逆名を issues にする。
5. agent-issue.tasks から agent-backlog への双方向リレーションを作り、逆名を issues にする。

接続先ツールのAPI形式に従い、逆列を同じ関係の一部として扱う。作成後の型・状態グループ・参照先と逆列の確認は、セットアップ手順5で行う。必要な型や参照先を作れない場合は、完了した段階と不足する機能を報告する。
