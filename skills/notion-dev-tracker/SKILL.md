# notion-dev-tracker

Notionを仕事の管理元として、人間とAIエージェントが合意した開発作業を計画・実行・検証・引き継ぐ。

## 対象を確認する

1. Gitルートの `.notion-dev-tracker.json`、リポジトリの指示、[DBスキーマと設定契約](references/schema.md) を読む。利用者のNotion接続で実スキーマ、データソースID、Projectページ、repositoryを取得し、対象remoteと照合する。未導入なら [Setup](../notion-dev-tracker-setup/SKILL.md) へ進む。未対応の設定・スキーマは不足・不整合を示して停止する。
2. 正式なタスク管理元を確認する。移行中なら既存の指定と合意を守る。新形式のタスク設定が有効でIssue接続だけが未設定ならタスク操作を継続し、Issueを「未設定・未確認」と報告する。取得失敗も0件として扱わない。
3. 一覧は必ずProjectで絞る。タスクは `project + task_id` で1件に特定し、0件・重複は調べて解決する。Issueは所属Projectを確認した実際のページIDで更新する。issue_idで依頼されても実ページと照合する。関連・依存も実ページで解決し、別Projectの同名データを推測で操作しない。

## 依頼に応じて読む

| 依頼 | 読む文書・進め方 |
| --- | --- |
| 現状・次の候補 | 下記の取得範囲で読み、進行・待機・候補と根拠を案内する。読み取りと提案に留める |
| Issueの登録・調査・タスク化 | [Issueの操作](references/issues.md) と [依頼別の境界](references/workflow.md) |
| タスクの作成・着手・実装・報告・受け入れ・再開 | [ワークフロー](references/workflow.md) と [タスク本文](references/task-template.md) |
| 合意済み範囲の順次実行 | [ワークフローの連続実行](references/workflow.md#連続実行)。明示的な依頼がある場合だけ行う |
| 新規導入・互換性のある再設定 | [Setup](../notion-dev-tracker-setup/SKILL.md) |
| 既存タスク管理の取込み | [Migrate](../notion-dev-tracker-migrate/SKILL.md)。具体的な移行案への同意後に取り込む |

## 取得範囲と正本

- 現状確認は未完了タスクと未処理Issueを中心に取得する。未割当・他セッション担当も含め、必要な関連・依存と本文をたどる。Issueの調査状態と関連タスクの実装状況を分け、未調査の関係は仮説と示す。
- 実装・再開は対象タスク、正本の仕様、必要な依存先、関連Issue、競合し得る作業を読む。関連Issueが `converted` でも必要な本文を確認する。常に全タスク本文を取得する必要はない。
- 全件監査・履歴確認・件数照合・移行は、完了済みを含め必要な範囲全体を取得する。
- 選んだ条件の一覧はページ送りを最後まで確認する。報告は取得条件・範囲を明示し、未取得範囲の合計を断定しない。

Notionは状態・優先順位・依存・承認・報告・受け入れの正本。コード・テスト・実行環境・版管理する規約はリポジトリに置く。仕様の正本の所在を示し、参照でつなぐ。ローカル出力は参照用とし、日々の状態をローカルJSON等と二重管理しない。

## 保存の共通手順

更新直前に対象を再読取し、自分が担当する列・本文だけ変更する。既存の関連と判断履歴を保持し、更新後にProject、状態、関係、保存内容を再取得して確認する。失敗・結果不明なら保存済み範囲を確認してから続け、重複作成や無根拠な成功報告を避ける。後続の着手判断に必要な共有情報を確認できなければ、新規着手を止める。

`agent_thread` と読取→更新→再読取は排他ロックではない。着手・権限・検証・停止の判断はワークフローと案件規約に従う。具体的なツール名・引数は接続環境で公開されている定義を使う。
