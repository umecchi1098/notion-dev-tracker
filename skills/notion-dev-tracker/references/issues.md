# Issueの操作

対象Projectの `agent-issue` を使う。列、状態キー、既存DBの選択肢への対応は [DBスキーマ](schema.md) とプロジェクト設定から解決し、操作範囲は [ワークフロー](workflow.md) に従う。Issueは気づきと調査の記録、backlogは実行するタスクとして扱う。新形式でIssue接続が未設定なら登録・調査の保存は行わず、未設定・未確認と示す。タスク操作は継続できる。

## 登録

name、対象projectを1件、statusの `untriaged` 値を設定する。種別が分かる場合は実DBのtypeから選ぶ。利用者の説明、再現条件、期待と実際の動作、添付や参照元など、得られた内容を本文に残す。不明な情報の追加入力を登録の条件にしない。

issue_idとcreated_atはNotionの自動設定値を使う。登録後にページID、対象Project、状態と自動採番IDを確認し、リンクを報告する。更新は対象Projectを確認した実際のページIDで行う。

## 調査とbacklog化

1. 対象IssueのProject・本文・tasksと、同じProjectの関連Issue・既存backlogを読む。調査や提案だけを求められている場合はその範囲を守り、保存も依頼の範囲に従う。通常の調査依頼では `investigating` とnext_actionを記録し、関連する既存実装、社内資料、必要なら公式資料を調べる。案件の規約に沿って可能な再現確認を行い、確認した事実、根拠、不明点、対応案を区別して本文に追記する。利用者の報告原文は保持する。
2. 対応案を既存backlogと照合し、扱える既存タスクは再利用する。追加作業は独立して受け入れられる単位に分け、[本文テンプレート](task-template.md)と[タスク作成手順](workflow.md#状態と遷移)に従って `planned` 登録する。元Issueのページ参照と調査根拠は初回作成から本文に含める。調査が未完了でも、必要な追加調査を独立したタスクとして具体化できれば登録できる。
3. tasksには同じProjectの関連タスクだけを設定する。各実ページのProjectを確認し、別Projectのtask_idや件名の一致から関連付けない。1つのIssueから複数タスク、複数Issueから1タスクへの関連付けを認める。tasksは逆参照issuesと同じ関係なので、既存の関連を保持して更新する。
4. 必要な対応が保存済みのタスクでカバーされたことを確認できたら、Issueを `converted` にする。情報不足や方針判断が必要で具体化できない部分が残る場合は `waiting` とし、必要な情報・判断をnext_actionに示す。一部をタスク化した場合も、残った論点と関連を記録する。見送りが利用者の判断や確認した仕様などで決まった場合は、根拠を本文へ残して `dismissed` にする。`converted`・`dismissed` では完了した調査のnext_actionを取り除き、タスクの次の操作はbacklog側へ残す。
5. Issueと作成・再利用したタスクを再取得し、対象Project、関連、状態、次の操作を確認して報告する。`converted` は受付処理の完了であり、実装や修正の完了はbacklogの検証・受け入れで判断する。

## 途中から再開する

保存されたIssueのtasksと、同じProjectのタスク本文にある元Issue参照を確認してから、未保存の作業を続ける。タスクを作った後でIssue更新に失敗した場合も、元Issue参照から作成済みページを探して関連を補う。同じ件名だけで同一と判断したり、調査のやり直しを理由に重複作成したりしない。保存済み範囲が確認できなければ新規タスクへの着手を止め、残る確認を報告する。

調査・登録の範囲内で具体化できたものは、毎回別の承認を求めず保存と確認まで進める。実装方針の選択や既存タスクの優先順位変更など、合意に含まれない判断が必要な部分を利用者に相談する。
